# 資產管理系統

手機 Chrome 就能用的個人資產登記與淨值 / 槓桿追蹤工具。
純靜態網頁（無需 build），後端用 **Supabase 免費方案**（Postgres 資料庫 + Email 登入）。

功能：
- **每日報價自動更新**：收盤價、期貨結算價、美股、美金匯率每天自動抓，手機不用開著，也不用自己改數字
- **記一筆交易**：選買/賣、打代號、輸入張數（或股數／口數）與價格，自動加減部位、重算均價
- **代號自動帶名稱**：台股打 `2330` 或「台積」就跳出台積電（上市＋上櫃約 2,700 檔）；期貨打「小台」自動帶每點價值
- **期貨**：指數期貨（大台/小台/微台/電子/金融）與**個股期貨**（大型 2 張、小型 100 股），權益數計入總資產、名目金額計入曝險
- **圖表**：圓餅圖可切換「資產組成」與「曝險明細」（每一檔股票、每一筆期貨各自的曝險佔比）；
  折線圖有資產走勢與槓桿走勢；**買賣收益**有累計已實現損益折線圖與單日長條圖
- **當沖**：同一天同一標的既有買也有賣會自動標記，收益分成「當沖」與「波段」兩欄
- **期貨也有平均成本與損益**，跟股票一樣；沒填成本就不顯示損益
- **歷史交易紀錄**，可刪除並自動還原部位
- **台指選擇權**：權利金市值計入資產、delta 曝險計入槓桿、最大風險獨立顯示。
  delta 由期交所每日結算價自動反推，不用手動輸入
- **權證**：輸入 6 碼代號即可，履約價、行使比例、到期日自動帶入；
  隱波、delta、theta、實質槓桿每日自動反推；**發行券商調降隱波會自動標示**
- **族群趨勢**：把成分股的月營收加總比去年同期，得出**整個產業的營收年增率**（39 個族群、184 檔）。
- **本益比**：近四季本益比每天自動抓官方公告；26/27/28 年預估本益比 = 現價 ÷ 預估 EPS，股價自動、預估自填。
- **心得與紀律**：每日交易日誌，加上會在下單當下跳出來的規則檢查。
- **期貨轉倉**：填兩個成交價，自動記成平倉＋建倉兩筆，並算好兩邊的手續費與交易稅。
- **報酬/波動**：用加權指數當及格線的選股計分，低於指數代表承受的波動換不到相稱的報酬。
- **美股 AI 產業地圖**：39 個族群、126 檔，用分析師的營收預估當前瞻的產業趨勢訊號。
  衡量的是產業景氣本身，不是股價漲跌
- 登記 **台股、期貨、選擇權、權證、複委託（USD）、現金、期貨權益數、負債**
- 自動算 **總資產、淨資產、槓桿①（資產槓桿）、槓桿②（曝險槓桿）**、目標達成率
- 一鍵存 **每日快照**，在「紀錄」看淨資產與槓桿的變化
- Email + 密碼登入，資料以 Row Level Security 隔離，只有自己看得到

## 1. 建立 Supabase 專案（免費）

1. 到 <https://supabase.com> 註冊，**New project**，區域選 Singapore 或 Tokyo（離台灣近）。
2. 左側 **SQL Editor → New query**，依序執行兩個檔案（都可重複執行）：
   - `supabase/schema.sql` — 建立資料表、RLS 政策與索引
   - `supabase/prices.sql` — 建立每日自動更新報價的排程
3. 左側 **Project Settings → API**，複製：
   - `Project URL`
   - `anon` `public` key
4. 打開 `config.js`，填入這兩個值：
   ```js
   export const SUPABASE_URL = 'https://xxxxxxxx.supabase.co';
   export const SUPABASE_ANON_KEY = 'eyJhbGciOi...';
   ```
   anon key 本來就是設計給前端用的，資料由資料庫的 RLS 保護，放在公開網頁沒問題。

## 2. 建立自己的帳號（建議做法）

個人使用最省事、也最安全的方式是**自己在後台建帳號、然後關閉公開註冊**：

1. **Authentication → Users → Add user → Create new user**，輸入 Email 與密碼，勾選 **Auto Confirm User**。
2. **Authentication → Sign In / Providers → Email**，關閉 **Allow new users to sign up**（可選，關掉後別人就不能在你的網站註冊）。

之後直接用網頁上的「登入」即可。若想改用網頁「註冊」功能也可以，Supabase 會寄確認信（免費方案每小時只有少量額度）。

## 3. 本機試跑

ES module 不能用 `file://` 直接開，需要一個靜態伺服器：

```powershell
cd asset-manager
python -m http.server 8000
# 開 http://localhost:8000
```

## 4. 部署到 GitHub Pages（讓手機可以用）

你已經有 `matthewhsieh.github.io` 這個 repo，把整個資料夾放進去即可：

```powershell
# 在 code 資料夾
Copy-Item -Recurse asset-manager matthewhsieh.github.io\asset-manager
cd matthewhsieh.github.io
git add asset-manager
git commit -m "add asset manager"
git push
```

幾分鐘後網址是 **https://matthewhsieh.github.io/asset-manager/**

然後回 Supabase：**Authentication → URL Configuration**
- **Site URL** 填 `https://matthewhsieh.github.io/asset-manager/`
- **Redirect URLs** 加同一個網址（忘記密碼、註冊確認信會導回這裡）

## 5. 手機使用

1. Android Chrome 開上面的網址並登入。
2. 右上角選單 → **加到主畫面**，之後就像 App 一樣全螢幕開啟。
3. 登入狀態會保留，不用每次輸入密碼。

## 數字定義

| 名稱 | 公式 |
|---|---|
| 總資產 | 台股市值 ＋ 複委託市值×匯率 ＋ **期貨帳戶權益數** ＋ 現金/存款 |
| 淨資產 | 總資產 － 負債 |
| 槓桿①（資產槓桿） | 總資產 ÷ 淨資產 |
| 槓桿②（曝險槓桿） | （台股市值 ＋ 複委託市值 ＋ 期貨名目）÷ **總資產**，指數期貨與個股期貨都算 |
| 指數期貨名目 | 口數 × 結算價 × 每點價值（大台 200 / 小台 50 / 微台 10 / 電子 4000 / 金融 1000） |
| 個股期貨名目 | 口數 × 標的股價 × 等同股數（**大型 2,000 股 ＝ 2 張**、**小型 100 股**） |
| 期貨損益 | 多單（現價 − 平均成本）、空單（平均成本 − 現價），再乘口數與規格 |
| 已實現損益 | 賣出時（成交價 − 平均成本）× 賣出數量；期貨平倉時只結算平掉的口數。買進不計 |
| 當沖 | 記交易時勾「當沖」。買賣自成一組結算，**完全不動長期部位的股數與均價** |
| 已實現損益 | 顯示的一律是**扣掉手續費與交易稅之後的淨額**，買進那一筆的手續費也算在內 |

### 當沖為什麼要獨立處理

如果當沖的標的剛好是你長期持有的，用一般方式記會出兩個問題：
買進那一筆會把長期部位的均價拉歪（而且是永久的），
賣出時的已實現損益會變成「賣價 − 混合後均價」而不是「賣價 − 當沖買價」。

實測：持有 5 張均價 2000，當沖 1 張 2440 買、2500 賣。
不勾當沖會算成賺 426,667 且均價變成 2073；勾了當沖是正確的 60,000，均價維持 2000。

所以當沖的兩筆都要勾「當沖」。系統用**先進先出**把同一天同標的的當沖買賣配對，
**一趟來回算一組**，損益掛在平倉的那一筆上。先買後賣、先賣後買、部分沖銷都支援。

同一檔一天來回兩趟不會被平均在一起。例如買 518 賣 525、再買 511 賣 510，
會分別顯示 +14,000 和 −2,000，而不是合併成 +12,000 一個數字，
否則看不出哪一趟做錯。

**當沖只認你勾選的，不做推斷。** 早期用「同一天同標的有買有賣」推斷會出錯：
例如當沖 1 口的同時又賣掉 5 口長期部位，那 5 口會被誤判成當沖。

**代號可以打中文。** 打「台玻」會自動換成 1802。這很重要，
因為一組當沖若一筆填代號、一筆填中文，會被當成兩個標的而配不成對，損益就消失了。
既有紀錄即使當初填了中文，現在也會正確配對。

**只有台股現股當沖有證交稅減半，期貨、選擇權、權證都沒有。**
| 選擇權權利金市值 | 口數 × 權利金 × 50，買方為正、賣方為負，計入總資產 |
| 選擇權 delta 曝險 | 口數 × delta × 隱含遠期指數 × 50，取絕對值加總後計入槓桿② |
| 選擇權最大風險 | 買方 = 權利金；賣方賣權 =（履約價 − 權利金）× 口數 × 50；賣方買權無上限 |
| 權證市值 | 張數 × 1000 × 權證價，計入總資產 |
| 權證 delta 曝險 | 張數 × 1000 × 行使比例 × delta × 標的股價，計入槓桿② |
| 權證最大損失 | 付出的權利金。權證只能做買方，不會賠更多 |

> **算不出 delta 的部位不會被安靜地漏掉。** 權證或選擇權若還沒算出 delta，
> 總覽的曝險區塊會直接標示「這些部位目前沒有計入總曝險，實際曝險比顯示的高」。

### 權證：隱含波動率才是真正的風險

權證的委買賣價由發行券商決定，計價參數裡**唯一能在發行後被人為調整的就是隱含波動率**。
券商調降隱波會直接讓權證價格下跌，而 delta 完全反映不出這件事。

所以系統每天把每檔持有權證的隱波反推出來存進 `warrant_iv_history`，
比對期間內的變化，被調降超過 0.5 個百分點就在「持倉」標示「隱波被調降」。
這是這個工具比券商 App 多做的一件事。

約半數權證當天沒有成交，這時用造市商的委買賣中價評價。
界限型與重設型（約佔 7%）Black-Scholes 不適用，這類會標示並開放手動填 delta。

### 交易成本

稅率是法定的，寫死在程式裡（查證日期 2026-09-08）：

| 商品 | 交易稅 |
|---|---|
| 台股賣出 | 0.3% |
| **台股當沖賣出** | **0.15%**（已延長至 2027-12-31） |
| 權證賣出 | 0.1% |
| 期貨（含個股期貨） | 契約金額 × 0.002%，**買賣各課一次** |
| 選擇權 | 權利金 × 0.1%，**買賣各課一次** |

手續費因券商與折數而異，在「設定 → 交易成本」自己填：台股費率與折數、每筆最低、
權證折數、期貨每口、選擇權每口、複委託費率。

**折數是跟券商談的，當沖和波段都一樣。當沖影響的只有政府的證交稅（0.3% 減半為 0.15%）。**

**期貨與選擇權是每口固定金額，買進收一次、賣出再收一次**，所以一口來回等於填的兩倍。
複委託也是買賣各收一次。

成本是依交易紀錄即時算出來的，不存在每一筆裡，所以改了費率設定會全部重算，
也不會動到既有的交易紀錄。「買賣收益」的圖表畫的是**淨損益**，
買進那一筆的手續費也算在內。

### 選擇權的 delta 怎麼算出來的

不折現的 Black-76 模型裡，理論價只取決於遠期價 F、履約價 K 與 `σ√T` 這個合成參數，
所以由市場權利金可以直接解出 `σ√T`，**不需要分別知道到期日與波動率**，
也就避開了期交所到期代碼（`202609` / `202609W2` / `202609F2`）換算成日期的麻煩。

遠期價 F 用選擇權鏈自己的買賣權平價反推（`F = K + C − P`，取價平那組），
與權利金同一天同一市場，不受期貨行情發布延遲影響。
實測買賣權平價檢查 `call delta − put delta = 1.000`，資料庫與參考實作的結果分毫不差。

**但書：** delta 曝險是線性近似。大幅波動時實際曝險會被 gamma 放大，賣方尤其明顯。
所以最大風險是獨立顯示的數字，不併進槓桿。

> 期貨的「權益數」是帳戶層級的一個數字，記在「資金」頁，只計入總資產一次；
> 各個部位的「名目金額」只影響曝險，不會重複計入資產。

## 每日自動更新

### 為什麼排程要拆成十個 job

**這是踩過的坑，不是設計偏好。** 原本全部串在一支 `update_all_prices()` 裡，
由五個 cron job 呼叫。結果：

1. `postgresql.conf` 把 `statement_timeout` 設成 **120 秒**，而那個值在語句開始時
   就鎖定了——**函式裡再 `set_config('statement_timeout','180s')` 也改不動已經在跑的語句**。
   實測 13 次排程有 **6 次**在兩分鐘被砍。
2. 整支是**一個交易**，被砍就全部 rollback——連前面已經抓好的行情、
   以及 `price_runs` 的日誌一起消失。**所以事後查 `price_runs` 會以為那次根本沒跑。**

症狀是使用者先發現的：「其他股票都正常，只有金居永遠慢一天」。
追下去才知道跟處置無關，是**上櫃**：

| | 資料來源 | 大約幾點更新 |
|---|---|---|
| 上市 | 證交所 MI_INDEX | 台北 **14:30** |
| 上櫃 | 櫃買 OpenAPI | 台北 **16:00 之後** |

原本 16:00 之後只剩兩班（18:00、21:00），而那兩班每次都在後面的美股階段被砍掉，
連帶把前面抓到的上櫃行情一起還原。所以上櫃股票整個交易日都停在前一天，
上市的則正常——看起來就像「只有金居壞掉」。

現在拆成每段一個 job，各自獨立交易，慢的那段掛掉不會拖累快的那段：

| job | UTC | 台北 | 內容 |
|---|---|---|---|
| `am-quotes-1..5` | 6:35 / 8:05 / 10:05 / 11:05 / 13:05 | 14:35 / 16:05 / **18:05** / **19:05** / 21:05 | 台股、期貨、選擇權、權證、匯率、寫回持倉（約 15 秒） |
| `am-fundamentals` | 8:20 | 16:20 | 估值、月營收、季報、交易所警示 |
| `am-estimates` | 8:40 | 16:40 | 分析師預估（每次 120 檔，挑最久沒更新的） |
| `am-risk` | 9:00 | 17:00 | 報酬/波動（172 檔約 80 秒） |
| `am-us` | 22:05 | 06:05 | 美股報價與產業（每次 60 檔） |
| `am-housekeeping` | 22:40 | 06:40 | 權證基本資料 20MB、月底快照、日誌清理 |

**18:05 與 19:05 那兩班是專門為了上櫃加的。**

`update_all_prices()` 保留給手動一次跑完用，但它需要一個沒有 120 秒上限的連線
（例如 Management API），不要再拿它當排程。

全部在 Supabase 資料庫裡用排程跑，手機關著也會更新，也不會用到你的電腦。

行情一天跑五次是因為**來源可能比排程晚發布**。抓到當天資料後，後面幾班會被守則擋掉，
不會重複下載（實測完整流程從 6 秒降到 1.5 秒，且不再打對方的 API）。
上市與上櫃各自判斷，其中一邊晚發布不會影響另一邊。

| 資料 | 來源 | 備註 |
|---|---|---|
| 上市股票 | 證交所「每日收盤行情」`MI_INDEX`，帶日期 | 以台北時區的日期往回找最近一個交易日。**不要用 `STOCK_DAY_ALL`**，實測會落後好幾天 |
| 上櫃股票 | 櫃買中心 `tpex_mainboard_daily_close_quotes` | 永遠回最新交易日 |

| 權證基本資料 | 證交所 `t187ap37_L` | 20MB、37,000 筆，只有除權息才會變，**每 6 天才重抓一次** |
| 權證每日報價 | 證交所 `MI_INDEX` type=0999 / 0999P | 含標的代號與標的收盤價，約 31,000 筆 |
| 指數期貨結算價 | 期交所 `DailyMarketReportFut` | 這個端點會在 JSON 與 CSV 間變換格式，程式兩種都吃；期交所發布本身有延遲 |
| 美金匯率 | Yahoo `TWD=X` | 期交所那份會落後數日，只當備援 |

| 月營收 | 證交所 `t187ap05_L`、櫃買中心 `mopsfin_t187ap05_O` | 每月 10 日前後更新。**單位是仟元**，1 億 = 100,000 |
| 季報 EPS | 證交所 `t187ap14_L`、櫃買中心 `mopsfin_t187ap14_O` | **年初到該季的累計值**，第 2 季就是上半年 |

| 報酬/波動 | Yahoo chart API，三年日線 | 上市 `.TW`、上櫃 `.TWO`。170 檔約 30 秒 |
| 美股 AI 產業 | stockanalysis `/stocks/<sym>/` + Yahoo chart | 營收與 EPS 預估。126 檔約 55 秒 |

每個市場的資料日期會顯示在「設定 → 行情更新」，若某個來源落後，總覽會直接標示，不會讓你誤以為是最新價。
每筆快照也會記錄 `price_as_of`（這筆是用哪一天的收盤價算的），在「紀錄」頁的「行情日」欄位；
若它比快照日期早會標紅，表示當時來源還沒發布。自動快照隔幾小時會用新價格覆蓋自己，會自動收斂到正確值。

- 個股期貨用**標的股票收盤價**計價，因為曝險的定義就是「等同 N 股現股」。
- 價格只會 `UPDATE`，**不會新增或刪除任何項目**；只有賣光時部位才會被移除。
- 想立刻更新：App 右上角 ↻，或到「設定 → 立即重新抓取報價」，約 6 秒。

> **為什麼手動更新是一項一項抓的。** Supabase 給 `authenticated` 角色的 statement_timeout 是 **8 秒**，
> 但七個來源一次跑完要 10 秒以上，權證基本資料更要 50 秒，所以一定會逾時。
> 手動更新改成呼叫 `refresh_market(kind)` 一次做一項，每項都遠低於 8 秒，
> 某一項失敗也不影響其他項。權證基本資料 20MB 不放進互動流程，只由排程處理。
> 目前的階段是 `tw` `fut` `opt` `war` `warp` `fx` `us` `val` `rev` `fin` `est` `risk` `usx` `sync`。
>
> **權證為什麼要拆成兩階段（`war` 認購 / `warp` 認售）。** 兩種一起跑實測 6.4 秒，
> 貼著 8 秒上限。證交所偶爾限流（實測 0999P 曾經一次要 10.2 秒，平常只要 0.7 秒）就直接逾時報錯。
> 拆開後認購 3.9 秒、認售 1.2 秒，被限流一次也還有餘裕，而且一邊失敗不影響另一邊。
>
> 拆的時候踩到一個坑：「已經有最新資料就跳過」原本是取全部權證的最大日期，
> 認購先跑完把日期推到今天，認售就會誤以為有資料而整個跳過。
> 要用 `src` 分認購認售各自判斷。另外**跳過時也要寫進執行紀錄**，
> 原本靜靜跳過會讓人以為壞掉了。
>
> **踩過的坑：函式裡不能寫沒有 WHERE 的 DELETE。** Supabase 對 PostgREST 的連線載入了
> `safeupdate`，它會擋掉沒有 WHERE 的 DELETE，而且 `SECURITY DEFINER` 切換角色時
> **不會卸載這個 session 設定**。症狀很難察覺：用 Management API（postgres session）跑得過，
> 但從 App 按「立即更新」一定失敗。實測選擇權結算價那段
> 2026-09-08 一天就失敗 7 次而畫面完全看不出來。清空暫存表要寫 `delete from x where true`。
> 其中 `est` 一次只抓 12 檔（挑最久沒更新的），因為每檔要 0.5 秒；排程則一次抓完。
- 排程狀態可查：SQL Editor 執行 `select * from price_runs order by id desc limit 20;`
- 各市場資料日期：`select * from price_status;`

想改定義，只要改 `app.js` 裡的 `compute()`。

## 記一筆交易的規則

| 情境 | 處理 |
|---|---|
| 台股 / 美股 買進 | 股數相加；均價 =（原股數×原均價 ＋ 新股數×成交價）÷ 總股數；現價更新為成交價 |
| 台股 / 美股 賣出 | 股數相減；均價不變；賣到 0 自動移除部位；賣超過持有會擋下 |
| 期貨 | 以淨口數計算：買進 +、賣出 −；穿越 0 自動翻多／翻空；歸零移除部位。新部位的「帳戶權益」要到持倉頁補填 |
| 刪除交易 | 若是該標的最新一筆，精確還原到交易前；否則只反向調整數量（均價不動） |
| 台股單位 | 預設「張」（1 張 = 1000 股），可切換成「股」 |

交易本身不會動現金餘額，現金請在「資金」頁自行維護。

## 族群趨勢怎麼算的

台灣強制上市櫃公司每月公告營收，是全球少見的高頻基本面資料。多數市場只有季報。

把一個族群的成分股營收加總，再比去年同月，就是這個產業的實際成長率。
比看股價漲跌更接近「產業趨勢」本身，因為股價已經含了預期與情緒。

族群分類在 `supabase/themes.sql`，人工維護，改完整段重跑即可。
目前 **39 個族群、184 檔**，從上游玻纖布一路到機殼、快接頭、探針卡、無塵室廠務。

分類原則是**寧可拆細也不要合併**。被動元件裡 MLCC、石英元件、電阻電感是三個完全不同的循環，
合在一起看只會互相抵銷掉訊號。一檔可以屬於多個族群（台玻同時在玻纖布與玻璃基板），各族群獨立加總。
族群至少三檔，只有一兩檔的「族群」其實是個股：銅箔（金居）與玻璃基板（台玻、富喬）是僅有的例外，
因為台灣純做這兩塊的上市公司就是這麼少，看它們的數字時要記得那其實是個股營收。

每筆營收公告都含「當月、上月、去年當月」三個數字，所以抓一次就能寫進三個月份，
歷史會隨每月公告自然累積，不需要另外補歷史資料。

**營收成長不等於股價會漲。** 但產業景氣的轉折通常先反映在營收，而營收是硬數字。

## 本益比怎麼來的

這頁分成兩件性質完全不同的事，混在一起看會出事。

### 近四季本益比：是事實，全自動

證交所與櫃買中心**每天公告**每一檔的本益比、股價淨值比與現金殖利率，
上市走 `BWIBBU_ALL`、上櫃走 `tpex_mainboard_peratio_analysis`，
存進 `valuation` 表，跟股價一起每天自動更新，不需要任何人工輸入。
涵蓋 1,969 檔，其中約 1,540 檔有本益比。

虧損的公司顯示「虧損」而不是 0。顯示 0 會讓人誤以為很便宜，那是最危險的誤讀。

### 26 / 27 / 28 年預估本益比：是猜測，要自己維護

公式是 **現價 ÷ 預估 EPS**。股價每天自動更新，所以比值每天都會變，這部分是自動的。
但**分母沒有免費 API**。台灣的分析師共識預估在 FactSet、彭博與券商報告裡，都要付費。

所以做法是把預估 EPS 存在資料庫：

| 表 | 來源 | 涵蓋 |
|---|---|---|
| `eps_override` | 你自己填的，受 RLS 保護 | 你想覆蓋的任何一檔 |
| `eps_estimate` | **自動抓自 stockanalysis.com**，每日排程 | 全部族群成分股，當年度與次年度 |
| `eps_forecast` | 人工整理自新聞與券商報告 | 少數幾檔，但有 2028 與詳細註解 |

優先順序是 **自填 > 自動 > 人工整理**。自動的比人工整理的新，所以排前面；
但註解一律沿用人工那份，因為那裡寫的是「這個數字能不能信」，跟數字本身一樣重要。
在「持倉」頁點任一列就能填自己的。留空就退回自動值。

#### 自動抓取是怎麼做到的

stockanalysis.com 的個股預估頁是 SvelteKit 做的，`__data.json` 端點會回傳整頁資料，
上市（`tpe`）與上櫃（`tpex`）都有。**當年度與次年度免費，再往後被鎖在 `[PRO]` 後面**，
所以 2028 仍然只能人工。190 檔約 40 秒，跑在每日排程裡。

資料是 devalue 的索引壓縮格式：物件裡每個「值」都是指向扁平陣列的索引而不是字面值，
所以要照索引鏈走 `estimates → stats → annual → epsThis → this`。
解析器在 `supabase/estimates.sql` 的 `pm_sa_parse()`，整個 pool 裡同時有 `stats` 與 `table`
兩個 key 的元素只有一個，定位是唯一的。

**踩過的坑**：一開始用「最後一個 eps 還是數字的年度」判斷當年度，結果整組年度往前位移一年，
因為有些公司當年度的 eps 欄位是 null（華新、上詮、聖暉、融程電）。
正確規則是「最後一個不是 `[PRO]` 的年度」。

#### 用官方財報當守門員

自動抓來的數字不能照單全收。做法是拿它跟證交所公告的季報累計 EPS 對：
**如果預估比「已經公告的年初至今累計」還低，而且還沒到第四季，那個預估一定有問題。**

107 檔裡抓到一檔：緯穎的自動預估 2026 年 120.3 元，但它上半年就已經賺了 156.4 元。
這種錯通常來自股數基期不對，會一路污染後面每一年，所以整條自動預估都丟掉、
退回人工整理的 FactSet 數字（361.05 / 545.97 / 636.80，前後才一致）。

**預估本益比的分母是別人的猜測。** 同一檔股票不同券商的 2028 年 EPS 可以差一倍，
算出來的本益比自然也差一倍。所以每筆預估都存來源與查證日期，三個月就該重看一次。

#### 覆蓋度：這才是最容易誤判的地方

同樣顯示成「26F 幾倍」，背後可能是 42 位分析師的共識，也可能是某篇新聞引述的無名「法人」。
所以每一筆都存分析師人數與可信度，**而且是逐年存的**，因為同一檔的不同年度差很多：

| 標的 | 2026 | 2027 | 2028 |
|---|---|---|---|
| 台積電 2330 | 40 位 | 42 位 | 42 位 |
| 奇鋐 3017 | 19 位 | 19 位 | 19 位 |
| 和碩 4938 | 8 位 | 9 位 | **1 位** |
| 神達 3706 | 4 位 | 4 位 | 無 |
| 金居 8358 | **1 位** | **1 位（只有高盛）** | **1 位（只有高盛）** |
| 台玻 1802 | **0 位（新聞引述無名法人）** | 無 | 無 |

人數兩位以下會標 ⚠，整檔沒有任何覆蓋的標「無人覆蓋」。一位分析師的預估不叫一致預期。

**台股大約只有六成的公司有人在報。** 39 個族群 171 檔裡，107 檔有預估、64 檔完全沒有。
「無人覆蓋」是常態不是錯誤。族群卡上的「N/M 檔有預估」如果分母遠大於分子，
那個族群的預估本益比中位數就別太當真。

#### 達成率

年初至今已實現 EPS ÷ 當年度預估。季報 EPS 來自證交所 `t187ap14_L` 與櫃買 `mopsfin_t187ap14_O`，
存在 `financials` 表，欄位是**年初到該季的累計值**，所以第 2 季就是上半年。

半年報時達成率應該在 50% 上下。明顯偏低就代表那個預估在賭下半年大爆發，
**這件事光看預估本益比是完全看不出來的**。目前四檔持股的達成率都在 38–42%，全部押在下半年。

### 複委託的手續費

費率 0.1%，**每筆最低 1 美元**（2026-09-10 填入）。
最低收費會在單筆金額低於 1,000 美元時生效，那時實際費率會高於 0.1%，
金額越小越明顯——100 美元的單，手續費就是 1%。

### 複委託的美股

Yahoo 的估值端點現在要 crumb 驗證，抓不到近四季本益比，所以那一欄是空的。
但股價一樣每天自動更新，只要自己填了預估 EPS，預估本益比照樣會每天重算。

### 族群本益比

「族群」頁每個族群顯示成分股本益比的**中位數**，不是平均。
一檔異常高就會把平均拉爛，中位數不會。虧損的公司不計入中位數，
但會另外標出有幾檔在虧損，那本身就是訊息。點開族群可以看到每一檔的本益比。

## 心得與紀律

交易日誌只會讓你**事後後悔**，規則檢查才會讓你**事前看見**。
手癢是在按下確定那一刻發生的，不是晚上寫日誌的時候。
所以這一頁不只是日記，規則會在記錄交易時就跳出來。

### 三張表

| 表 | 內容 |
|---|---|
| `journal` | 一天一則心得，可隨時回頭改。另存當天的已實現損益與紀律自評 |
| `rules` | 自己定的規則。`kind` 決定程式怎麼檢查，`started_on` 記錄什麼時候下的決心 |
| `rule_breaks` | 違規紀錄，用來算「連續幾個交易日沒違規」 |

三張都是使用者資料，受 RLS 保護，程式更新不會動到。

### 會自動檢查的規則

| `kind` | 檢查什麼 |
|---|---|
| `opt_only_hedge` | 選擇權只准 buy put 與 sell call。買 call 或賣 put 就是違規 |
| `day_one_at_a_time` | 手上那檔當沖沒歸零就開下一檔 |
| `day_max_amount` | 個股當沖單筆金額超過上限 |
| `scale_in` / `free` | 只提醒，不自動判斷 |

紀錄頁的交易列表可以切換**全部 / 當沖 / 波段 / 轉倉**，並按日期分組，每天右邊是當日該分類的小計。

**轉倉一定要獨立一類。** 它的已實現損益只是把原本就存在的未實現入帳，不是那天做出來的績效。
2026-09-10 就是實例：台玻轉倉一筆 −130,992 跟當天當沖 +22,603 混在一起，
帳面顯示 −109,416，會以為當沖在虧錢，其實那天當沖是賺的。

**規則不會擋住存檔。** 那是你的錢、你的帳。
但存檔前會跳一個確認要你自己按下去，而且違規會被記下來、每天在心得頁攤開。

**系統跟券商的下單 App 沒有連線，所以擋不到下單。** 實際使用上常常是下單完才回來記錄，
所以規則分兩種：從記錄下來的資料就算得出來的（選擇權類型、當沖檔數與金額）會自動標「今天違反」；
需要盤中資訊才能判斷的（例如「不放空當天強勢股」）事後無從檢查，只能當提醒。
做過即時查盤中報價的版本，但既然是事後記錄，那個檢查永遠來不及，所以拿掉了。

一次一檔的檢查是**依時間重播**當天的當沖：只要在還有未平倉部位時開了另一檔就算。
不是只看當下有沒有兩檔，因為那樣事後就查不出來了。

### 為什麼把紀律和損益分開看

心得頁的自評問的是「有沒有照規則做」，不是「賺還是賠」。
兩者混在一起最危險的後果是：**在賺錢的月份把壞習慣一起放大。**
守規則卻賠錢是可以接受的，破規則卻賺錢才是最貴的一次經驗。

## 報酬 ÷ 波動：選股的及格線

「這檔漲很多」是最會騙人的說法。**漲得多不等於賺得多。**

2022-2026 實測，把每個標的都調整到跟加權指數一樣的波動之後再比：

| 標的 | 買進持有 | 年化波動 | 報酬/波動 | 套上同一條交易規則 |
|---|---|---|---|---|
| 奇鋐 | 36.84x | 53.9% | **2.33** | 13.10x |
| 台光電 | 20.32x | 49.8% | **1.95** | 9.43x |
| 台積電 | 3.88x | 30.2% | 1.18 | 9.76x |
| 加權指數 | 2.67x | 21.2% | 1.17 | 7.75x |
| 金居 | 7.79x | 52.4% | 1.13 | **4.03x** |
| 台玻 | 2.61x | 50.9% | 0.48 | 2.02x |
| 和碩 | 1.31x | 28.0% | 0.23 | 2.58x |

**金居三年漲 7.79 倍看起來很猛，但波動 52% 讓風險等價槓桿只能開 0.81 倍，
套上同一條規則後只有 4.03 倍，反而輸給指數的 7.75 倍。**

所以判斷一檔值不值得買，看的是「每承受一單位波動換到多少報酬」。
加權指數這個比值就是及格線。低於它的個股，不如直接開槓桿買指數，還省下選錯的風險。
一檔波動 50% 的股票，年化要超過 58% 才配得上它的風險。

### 實作

`risk_stats` 表，欄位是三年年化報酬、年化波動、比值、最大回撤、近一年波動。
資料來自 Yahoo Finance 的 chart API，一次請求給三年日線，上市 `<代號>.TW`、上櫃 `<代號>.TWO`。
170 檔約 30 秒，跑在每日排程裡。加權指數也存一筆（symbol `TAIEX`）當基準線。

族群頁的每一檔都會顯示比值，贏過指數的標「贏指數」。族群卡顯示中位數與「N/M 檔贏過指數」。
持倉頁的每個標的也會顯示，並直接跟指數對照。

## 美股 AI 產業地圖

族群頁上方可以切換台股／美股。兩邊的訊號方向**相反**：

| | 台股 | 美股 |
|---|---|---|
| 訊號 | 已公告的每月營收 | 分析師的營收預估 |
| 性質 | 落後指標，是事實 | 前瞻指標，是猜測 |
| 基準線 | 加權指數 | 那斯達克 100 |

美股沒有月營收，但 stockanalysis 的預估頁同時給本年度與次年度的**營收**預估。
把族群成分股的營收預估加總再比，就是這個產業被預期要長多快。
39 個族群、126 檔，每天自動更新，一輪約 55 秒。

分類原則跟台股那邊一樣：**寧可拆細也不要合併。** 一開始只分 17 個族群，
把「電力」放成一格，看起來明年只成長 4.7%，結論會是「AI 缺電的故事沒反映在營收」。
拆細之後才看得出來那一格其實是四個完全不同的東西：

| 拆出來的族群 | 明年營收年增 | 說明 |
|---|---|---|
| 小型模組核能 SMR | **+439%** | 但營收基期趨近於零，是純故事 |
| 發電設備 渦輪機 | +14.0% | 只有 GEV，報酬/波動 2.39 |
| 資料中心工程營造 | +14.3% | 蓋機房的人，7 檔裡 3 檔贏 NDX |
| 電力設備 開關 | +10.9% | |
| 電力供應商 IPP | **+4.1%** | 電力公司本身幾乎不成長 |

記憶體也一樣。原本一格 +61.6%，拆開是 DRAM/HBM +85.8%（明年本益比 6.5 倍）、
NAND SSD +23.3%、硬碟企業儲存 +24.8%，三個完全不同的循環。

**各公司會計年度不一致**，例如 NVDA 的 FY2027 其實是 2026 曆年，
所以欄位存的是「本年／明年」而不是寫死年份。

### 兩個資料陷阱

**一、上市未滿兩年的不給報酬/波動比值。** 把 1.5 年的報酬年化再標成「三年」會產生假的高分。
SNDK 2025-02 才從 WDC 分拆，只有 392 個交易日，原本算出來比值 10.57，
拿去跟真的跑滿三年的公司比完全沒有意義。現在門檻設在 500 個交易日，
未達標的顯示「上市未滿兩年」，波動仍然保留（200 天估波動就夠）。
修掉之後記憶體族群的中位數從 2.65 修正成 2.54，贏過 NDX 的從 4/4 變成 3/4。

**二、`create table if not exists` 不會幫既有的表加欄位。** 新欄位一律要寫
`alter table ... add column if not exists`，否則函式會找不到欄位而整個檔案套用失敗。

## 處置股與注意股

總覽頁最上面：**持倉裡有被交易所盯上的就直接列出來。**
個股速覽也會在最上面掛一條警示帶，持倉列上有紅色標記。

### 為什麼值得做

他的做法是「一次只沖一檔、每檔上限 100 萬」。處置期間改成**人工撮合**，
達到門檻的委託還要**圈存**——買進先付全部價金、賣出先有券，**當沖等於做不成**。
撞上了才發現就來不及了。

實例：2026-09-10 查出來 **8358 金居正在處置中**（09-02～09-10），而他有 3 口個股期。

### 數字一律照抄公告，不要自己歸納

我原本寫「第二次處置就是全額圈存」，那是錯的。實測十三檔在處置中的：

| 項目 | 實際範圍 |
|---|---|
| 撮合間隔 | **2 / 45 分鐘都有**，不是固定值 |
| 圈存門檻 | 有的是**所有委託**，有的要**單筆 10 張以上**才算 |

金居的公告寫的是「單筆達 10 交易單位或多筆累積達 30 交易單位以上時」才圈存，
沒到那個量還是照常委託。所以 `pm_disp_match()` 與 `pm_disp_prepay()` 是從公告原文
用 regex 讀出來的，畫面顯示的是那一檔自己的數字，原文也可以展開看。

證交所寫國字（「約每二分鐘」），櫃買寫阿拉伯數字（「約每2分鐘」），兩種都要吃。

### 六個來源

| 等級 | 上市 | 上櫃 |
|---|---|---|
| `punish` 處置中 | `announcement/punish` | `tpex_disposal_information` |
| `near` 快達門檻 | `announcement/notetrans` | `tpex_trading_warning_note` |
| `notice` 注意股 | `announcement/notice` | `tpex_trading_warning_information` |

**證交所的注意股不帶日期參數會回空的**，一定要給 `startDate`/`endDate`；
當天收盤後才公布，所以抓最近兩週的區間。上櫃的注意股只給當天，
所以「近 30 天幾次注意」這個數字實際上只有上市股票算得準。

### 一個踩過的坑

`pm_roc_range()` 一開始用 `regexp_replace(t, '[^0-9]+', '|')` 來切「115/09/07～115/09/15」，
結果**連日期裡的斜線一起切掉**，變成六段，取第一段只剩 `115`，整個處置期間都是 null。
只能切 `[～~至]`。

## 選股

族群頁的第四個切換，**台股與美股都有**。這頁是把「在下跌中買入好公司」拆成可以按的條件。

### 池子有多大

| | 範圍 | 檔數 |
|---|---|---|
| 台股 | 全市場有公告月營收的普通股 | 約 **1,970** |
| 美股 | 日成交額 **2,000 萬美元**以上 | 約 **2,060** |

原本只能在 39 個族群的 171 檔裡挑，那是「已經有人整理過的」，
等於先幫自己把答案範圍縮小了。

**美股為什麼設流動性門檻而不是全開。** 美國有 7,100 檔上市股票，
一半以上一天成交不到兩百萬美元。那種標的就算篩出來也不能買——進得去出不來。
門檻取的是「曾經達到過」而不是「今天達到」，因為單日成交量會被法說會、
除息、指數調整帶偏，用當日值會讓池子每天進進出出。

台股不設門檻，全市場才 1,970 檔，而且他本來就在這個市場裡交易。

### 為什麼改成伺服器端篩

四千列不可能每次登入都載下來，手機更明顯。篩選與排序都在資料庫做
（`screen_stocks()`），一次只回前 60 檔。代價是拉桿要等一次往返，
所以拉桿有防連點——只認最後一次的結果，免得舊的蓋掉新的。

### 資料是怎麼補齊的

`market_prices`、`valuation`、`revenue`、`financials` 本來就是全市場（約 1,970 檔），
缺的只有 **`risk_stats`（報酬/波動與價格區間）**，原本只有 172 檔。

那個要一檔打一次 Yahoo 三年日線。實測 **300 檔約 50 秒**，全市場一輪要 5 分鐘以上，
遠超過 cron 的 120 秒上限，所以靠 `order by updated_at nulls first` **分批輪替**：
每班只做最久沒更新的 600 檔，台股一天四班、美股一天四班，各自一天輪完一圈。
波動與三年報酬是月級的變化，這個頻率夠了。

美股的風險統計另外寫了 `refresh_us_risk()`，**只打 Yahoo 不碰 stockanalysis**——
後者每檔要多一個請求，2,000 檔就是多 2,000 次，而選股需要的只有價格區間與報酬/波動。
分析師預估留給 AI 產業地圖那 126 檔，那裡本益比才是重點。

### 用關鍵字找「不好找」的那種分類

選股頁上面有一個搜尋框，打在**代號、名稱、族群、產業別、主要經營業務**上。

這是為了解決市場綽號查不到的問題。例如 **4989 榮科**，市場上叫它「小金居」——
那個綽號在任何欄位裡都查不到，證交所的產業別只寫「電子零組件業」，
它也還沒被分進任何族群。但它在公開資訊觀測站申報的主要經營業務寫著
**「電解銅箔之製造及銷售」**，所以搜「銅箔」就找得到。

實測搜「銅箔」還額外撈出 **2009 第一銅**，那也是一檔沒被分類過的。

### 主要經營業務是哪來的

`company_profile` 表，來源是公開資訊觀測站的 `ajax_t05st03`。
證交所的「產業別」太粗——金居、台光電、國巨、禾伸堂全都叫「電子零組件業」——
公司自己申報的這一行才分得出誰在做什麼：

| | 主要經營業務 |
|---|---|
| 8358 金居 | 電子零組件製造業、金屬表面處理業、鍊銅業 |
| 4989 榮科 | 電解銅箔之製造及銷售 |
| 6274 台燿 | 銅箔基板、粘合片、多層壓合板之製造、加工及買賣 |
| 2492 華新科 | 積層陶瓷及圓板電容、晶片電阻及保險絲、電感、射頻元件製造銷售 |

**為什麼是這個來源**：stockanalysis 的英文描述對上櫃覆蓋不全（金居本身就 404）；
官方的 `t187ap03_L` 基本資料沒有業務欄位，只有地址與董監；
MOPS 的彙總表也不含這一欄，只有單檔頁面有。所以只能一檔一個 POST。

#### 三個踩過的坑

**一、Postgres 正則的貪婪性由「第一個有偏好的量詞」決定。**
寫成 `'...</th>\s*<td[^>]*>(.*?)(?:</td>|<tr)'` 時，第一個量詞是貪婪的 `\s*`，
**整條式子就變成貪婪，後面 `.*?` 的問號完全失效**，一路吃到頁尾——
業務描述後面黏著董監、會計師、公司網址。前面的量詞也要一起寫成非貪婪。

**二、MOPS 的 HTML 有些列沒有 `</td>`。** 終止條件要同時含 `</td>`、`<tr`、`<th`，
取最先出現的那個。只用 `</td>` 會吃到下三個欄位；只用 `[^<]*` 又會被內容裡的
`<br>` 截斷（大成「飼料、大宗油脂、肉品」只剩「飼料」）。

**三、MOPS 會限流，而且不是回 HTTP 錯誤，是回一頁沒有那個欄位的 HTML。**
所以失敗看起來像「這家公司沒填」。實測一批 200 檔只成功 116 檔。
加上每檔 0.4 秒間隔之後變成 40 檔成功 37 檔。
另外排序要把**還沒抓到的排最前面**，否則失敗的那些會排到隊尾，要等一整輪才重試。

### 一個踩到的坑：PostgREST 只回前 1,000 列

`risk_stats` 從 172 列長到 1,975 列之後，前端原本那句
`sb.from('risk_stats').select(...)` **安靜地只拿到前 1,000 列**。
Supabase 的 `db-max-rows` 預設就是 1,000，不會報錯、不會警告。

**症狀很難察覺**：畫面不會壞，只是有些股票的報酬/波動、價格區間莫名變成「–」，
價格變成 0。像是資料還沒抓，其實是被截斷。

修法是兩邊都補：

| 用途 | 做法 |
|---|---|
| 整批載（族群頁、持股估值列） | 改用 `app_risk()`，只回**真的用得到的那幾百檔**——兩個基準指數、族群成分股、自己的持股，共約 300 列 |
| 個股速覽（任何一檔都可能被點到） | 風險與價格區間改由 `stock_detail()` 一起回，先畫得出來的先畫，其餘等 RPC 回來再補 |

`app_risk()` 是 `security definer`，會繞過 RLS，所以裡面查 `stocks`/`futures`/
`warrants`/`us_stocks` 時**一定要自己加 `auth.uid()`**，
否則會把別人持有哪些代號一起回出去，匿名瀏覽時更明顯。

### 本益比的來源會標出來

台股優先用分析師預估，**沒有預估的退回官方每日公告的近四季**，括號裡標是哪一種。
這件事很重要：台股只有大約六成有人覆蓋，如果沒有這個 fallback，
四成的股票會因為「沒有本益比」被本益比條件直接濾掉，而那不是它們貴或便宜的證據。

### 舊版的條件

**這頁挑出來的是候選，不是買進訊號。**

| 條件 | 意思 |
|---|---|
| 報酬/波動贏過大盤 | 好公司。低於這條線的，不如直接開槓桿買指數 |
| 從三年高點至少跌 N% | 在下跌中 |
| 至少三位分析師 | 避開沒人看的 |
| 排除處置與注意股 | 進去會卡住（只有台股有） |
| 本益比上限 | 0 = 不限 |
| 營收年增下限 | 台股是月營收年增（已發生），美股是明年預估（前瞻） |

排序可切「跌最多／報酬波動／本益比／營收成長」。
「距高點」用三年最高收盤，跟波動、報酬取自同一份 Yahoo 日線，一定一致。

跌得深有兩種原因——被錯殺，或基本面真的壞了——這頁分不出來，
要點進去看營收與預估。**報酬/波動需要三年日線，上市未滿兩年的算不出來，
會被「贏過大盤」這個條件濾掉**，那是刻意的，不是漏掉。

## 今日：哪個族群在動

族群頁的第三個切換（只有台股有）。**這頁是為了執行「不放空當天強勢的股票」那條紀律做的。**

要能執行那條規則，得先看得到兩件事：今天是不是**整群**在漲，以及一檔股票
**從當日低點拉了多少**。第二個才是判準。

### 為什麼不是看對昨收的漲跌幅

華新科 2026-09-10 是活教材：

| 看法 | 數字 | 會做出的判斷 |
|---|---|---|
| 對昨收 | 收 334、昨收 319.5，**+4.5%** | 「還好，沒有很強」 |
| 從當日低點 | 低 303 → 收 334，**+10.2%** | 「今天有人一路買上去」 |
| 它的族群 | MLCC 電容當天中位數 **+2.89%**，4 檔漲 3 | 「整群在漲，不要碰」 |

實際發生的事：在 317.5 空 2 口、328 回補，賠 42,000。
**只看對昨收的漲跌幅會做出完全相反的判斷。**

### 畫面

族群依當日中位數排序（不取平均，一檔漲停就會把平均拉爛）。
中位數 >2% 且過半上漲的標「整群在漲」紅框——**那是不能去空的族群。**
每一列給檔數、漲跌家數、從低點拉起的中位數、當天最強的那一檔（可以點開）。

個股速覽上也有同一組數字，從低點拉起超過 5% 會直接跳出提醒。

### 資料

`market_prices` 加了 `chg / open / high / low`，**跟收盤價同一個請求裡本來就有的欄位**，
沒有多打任何一次 API。證交所把漲跌方向包在 HTML 裡（`<p style= color:green>-</p>`），
所以正負號要用字串比對第 9 欄，第 10 欄才是絕對值；櫃買的 `Change` 直接帶正負號。

`theme_day()` 與 `stock_day(symbols)` 在 `supabase/theme_day.sql`。

**這是收盤資料，不是即時報價。** 用途是隔天回頭檢查自己昨天做了什麼，
不是盤中攔截——系統跟下單 App 沒有連線，下單完才回來記錄是常態。

## 個股速覽

在任何列了股票的地方點下去，都會開一張唯讀的速覽卡：

| 入口 | 怎麼點 |
|---|---|
| 持倉頁（台股／期貨／複委託／權證） | 標題旁邊那顆 **ⓘ** |
| 紀錄頁的每一筆交易 | 同樣是 **ⓘ** |
| 族群頁的成分股 | 整列可點 |
| 產業鏈的成分股 | 整顆藥丸可點 |

權證點的是**標的股票**，不是權證本身。ⓘ 一定要用 `stopPropagation` 擋住冒泡，
否則在持倉頁會變成開編輯視窗、在紀錄頁會變成刪除那筆交易。

### 卡片上有什麼

價格區間、我的部位、我在這一檔的成績、估值、風險、營收、族群與供應鏈位置。

**最上面那兩條區間帶是刻意放的。** 使用者的策略是「在下跌中買好公司」，
那就需要「現在站在哪裡」，而不是只有報酬與波動。金居是最好的例子：
三年最低 38.55、最高 700、現在 526——「三年漲 13 倍」跟「離高點還有 25%」
是兩種完全不同的判斷，只看前者會錯過它其實已經從谷底漲了 1,264%。

「我在這一檔的成績」是這個帳號所有相關交易扣掉手續費與稅之後的淨額，
還拆成當沖／波段／轉倉。台玻那張卡直接寫著已實現 −160,881，其中轉倉 −131,963、
當沖 −28,918——**族群數字說這檔好不好，這一行說我在這檔上做得好不好，兩件事常常相反。**

### 資料怎麼來的

分兩段，因為要點下去就立刻看得到：

1. **先用記憶體畫**。價格、本益比、報酬/波動、營收年增、族群、我的部位與交易
   在登入時就整批載好了，不必等網路。
2. **再補深度資料**。`stock_detail(p_market, p_symbol)` 一次往返補上股價淨值比、
   殖利率、產業別、季報累計 EPS、每一年的預估（含 2028 與但書）、上月與去年同月營收。
   拿不到就算了，該有的都已經在畫面上。

預估的**但書比數字重要**，收在「預估的來源與但書」那個摺疊區裡。
台玻 2026 年 EPS 1.7 那筆寫的是「這不是分析師共識，是新聞引述的無名法人數字」——
沒有這句話，1.7 看起來就跟真的共識一樣。

### 價格區間怎麼算的

`risk_stats` 與 `us_stats` 各加了 `hi52 / lo52 / hi3y / lo3y / last`。
這些值本來就在算波動用的那份 Yahoo 三年日線裡，順手算完，**沒有多打一次請求**。
`pm_risk_calc` 改了回傳欄位，所以要先 `drop function` 才能重建
（`create or replace` 不能改回傳型別）。

「位置 65%」的意思是現價落在區間的第 65 個百分點，0% 貼著最低、100% 貼著最高。

## 產業鏈：樹狀圖與關係圖

族群頁上面有兩排切換：**台股／美股**，以及**清單／產業鏈**。
清單是原本按成長率排序的排行榜，產業鏈是新的樹狀圖。

**為什麼要做這個。** 平的清單 39 個並排，看不出誰餵誰。
投資 AI 供應鏈最常犯的錯是**買到同一個部位三次**——
玻纖布 → CCL 銅箔基板 → PCB → 伺服器組裝是同一條鏈，
分開看像四個標的，實際上是一個賭注。攤開才知道自己重複押在哪一段。

### 兩張表

`supabase/theme_tree.sql` 建 `theme_meta` 與 `theme_links`，
台股美股各 39 個族群、共約 80 條供應鏈關係，全部人工整理。

| 表 | 內容 |
|---|---|
| `theme_meta` | 每個族群屬於哪個**大類**、在供應鏈的哪一段（**上游／中游／下游**）、排序 |
| `theme_links` | `src → dst` 代表 **src 出貨給 dst**，`note` 寫這條關係實際上在賣什麼 |

`note` 是這張表最有價值的欄位，寫的是瓶頸在哪裡而不是類別名稱。
例如玻纖布 → CCL 那條寫的是「低介電玻纖布，M8 以上的真正瓶頸」。

另外建了 `theme_tree(p_market)` 與 `theme_chain(p_market, p_theme)` 兩個 RPC，
不過畫面沒有用到——兩張表加起來才幾百列，登入時整批抓下來放記憶體，
點開上下游是零往返，比每次打 RPC 快得多。RPC 留著給之後用。

### 畫面怎麼看

每個族群一列，顯示成長率、幾檔、報酬/波動、本益比，右邊寫**上游 N・下游 N**。
台股的成長率是月營收年增（已發生），美股是明年營收預估（前瞻），兩邊定義不同不能混比。
自己有持股的族群左邊會有一條藍線與「持有」標籤。

**點一個族群**會展開它的上游、下游與成分股。上下游是可以按的，
按了會捲到那個族群並展開，等於順著供應鏈一路點下去。

### 套用

在 Supabase SQL Editor 貼 `supabase/theme_tree.sql` 執行一次即可，可重複執行。
新增族群時記得同時補 `theme_meta`，否則新族群會出現在清單但不會出現在樹上。

## 資料庫會不會塞爆

不會。實測 39 MB，免費方案 500 MB。

| 表 | 現在 | 年增 | 為什麼會長 |
|---|---|---|---|
| price_runs | 0.1M | 6.5M | 純日誌，**沒有上限** |
| warrant_info | 10.2M | 4.9M | 權證每月約 1,500 檔新掛牌，到期的不會自己消失 |
| price_history | 3.6M | 4.8M | 每月底存一次全市場收盤 |
| revenue | 1.2M | 4.6M | 每月約 1,975 家公告 |

其餘都是 UPSERT 或人工維護，列數固定。**每年約成長 27 MB，可以撐 17 年**，
就算成長比預估快三倍也還有 6 年。

唯一處理掉的是 `price_runs`：它是純日誌卻佔年成長的 24%，已加上只留 60 天的清理。

## 期貨轉倉

「持倉」頁最上面、藍色「＋ 記一筆交易」正下方那一顆 **⇄ 期貨轉倉**。
選部位、填兩個成交價，兩筆交易一起記好。「總覽」頁與期貨卡片右下角也各有一個入口。

> 一開始只放在期貨卡片右下角，又小又暗還要往下捲，實測根本找不到。
> 轉倉在使用者心裡是「一種交易」，就該放在記一筆交易旁邊。

轉倉的本質是**部位沒有變，但成本基礎重設，而且近月的損益要實現**。
多單轉倉是賣掉近月加買進遠月，口數一樣；空單反過來。
**順序不能反**，要先平倉才會用舊均價算出實現損益，先建倉的話均價會先被拉走。

### 兩件常被混為一談的事

畫面上刻意分開寫，因為混在一起會嚇到自己：

| | 是什麼 |
|---|---|
| **轉倉成本** | 遠月與近月的價差，加上兩邊的手續費與交易稅。**這才是轉倉真正花掉的錢** |
| **平倉實現損益** | 這筆損益早就存在了（未實現），轉倉只是讓它入帳，不是轉倉造成的 |

以台玻 30 口、均價 61.767、近月 60.3、遠月 60.1 為例：

```
轉倉成本 -10,056 元（價差 -12,000  手續費 1,800  交易稅 144）
同時實現原本的未實現損益 -88,020（均價 61.77 → 60.10）
```

轉倉其實**賺** 10,056（遠月比近月便宜 0.2，賣高買低），
那個 -88,020 是本來就在的帳面虧損變成已實現，不是轉倉的代價。

費用照期貨的規則算：手續費每口每邊 30 元、交易稅契約金額 0.002% 每邊各一次，
所以一次轉倉是兩邊都收。可以只轉一部分，口數超過持有量會擋下來。

### 為什麼不自動帶價格

做過了，但**實際成交價跟結算價本來就不一樣**，自己填反而準。
抓各月份結算價的程式留在 `supabase/futures_roll.sql`，沒有接進排程，
想啟用只要在 `update_all_prices` 與 `refresh_market('fut')` 各加一行。
股票期貨的契約代號對照（台玻 1802 → KU → KUF，252 檔）在 `supabase/fut_codes.sql`。

## 免登入瀏覽

登入畫面最下面有「不登入，先看產業地圖」。訪客只看得到**族群**那一頁
（清單／產業鏈／今日／選股四個切換都在），底下其他六個分頁直接隱藏，
右上角的 ↻ 也拿掉——抓資料的 RPC 沒有開給匿名。

個股速覽對訪客會少掉「我的部位」與「我在這一檔的成績」，改成一行提示。

### 開放的方式

`supabase/public_read.sql`。市場資料的表**一張一張列出來**加 anon 的 select policy，
不用「除了這幾張以外都開」的寫法——**漏掉一張就是把買賣紀錄公開**，
寧可以後新增表時要記得回來補一行。

**驗證不能看「有沒有 GRANT SELECT 給 anon」。** Supabase 預設就把 public schema
底下所有表的 SELECT 給 anon，十三張個人資料表全都有——真正擋住的是 RLS。
所以檔案最後驗的是：個人資料表都有開 RLS，而且沒有任何 policy 把 anon 或 PUBLIC 放進 roles。

### 順手補掉的一個洞

查權限的時候發現 **56 支函式是匿名可執行的**，因為
**PostgreSQL 建新函式時預設就把 EXECUTE 給 PUBLIC**。裡面包括：

| 函式 | 拿著公開的 anon key 能做什麼 |
|---|---|
| `pm_fetch(url)` | security definer，**從資料庫對任意網址發 HTTP GET**——等於把資料庫當跳板 |
| `refresh_warrant_info()` | 一次下載 20MB，免費的流量炸彈 |
| `snapshot_month_end()` | 寫進 snapshots |

現在的做法是先 revoke public schema 底下所有函式的 PUBLIC 與 anon 權限，
再把該開的十二支開給 anon、十七支開給 authenticated，最後驗一次對外清單。
**日後新增函式一定要重跑 `public_read.sql`**，否則又會預設全開。

## 資料安全

**更新程式不會動到已輸入的資料與買賣紀錄。** schema 變更一律只做 `add column if not exists`
這類新增動作，不 drop、不 rename、不重算既有的部位、成本與交易。
排程只會更新 `price` 欄位；股數、口數、成本、金額這些你輸入的數字永遠不動。
