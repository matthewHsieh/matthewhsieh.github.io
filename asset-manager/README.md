# 資產管理系統

手機 Chrome 就能用的個人資產登記與淨值 / 槓桿追蹤工具。
純靜態網頁（無需 build），後端用 **Supabase 免費方案**（Postgres 資料庫 + Email 登入）。

功能：
- **每日報價自動更新**：收盤價、期貨結算價、美股、美金匯率每天自動抓，手機不用開著，也不用自己改數字
- **記一筆交易**：選買/賣、打代號、輸入張數（或股數／口數）與價格，自動加減部位、重算均價
- **代號自動帶名稱**：台股打 `2330` 或「台積」就跳出台積電（上市＋上櫃約 2,700 檔）；期貨打「小台」自動帶每點價值
- **期貨**：指數期貨（大台/小台/微台/電子/金融）與**個股期貨**（大型 2 張、小型 100 股），權益數計入總資產、名目金額計入曝險
- **圖表**：圓餅圖可切換「資產組成」與「曝險明細」（每一檔股票、每一筆期貨各自的曝險佔比）；
  折線圖有資產走勢與槓桿走勢；**買賣收益**有累計已實現損益折線圖與單日長條圖
- **當沖**：同一天同一標的既有買也有賣會自動標記，收益分成「當沖」與「波段」兩欄
- **期貨也有平均成本與損益**，跟股票一樣；沒填成本就不顯示損益
- **歷史交易紀錄**，可刪除並自動還原部位
- **台指選擇權**：權利金市值計入資產、delta 曝險計入槓桿、最大風險獨立顯示。
  delta 由期交所每日結算價自動反推，不用手動輸入
- **權證**：輸入 6 碼代號即可，履約價、行使比例、到期日自動帶入；
  隱波、delta、theta、實質槓桿每日自動反推；**發行券商調降隱波會自動標示**
- **族群趨勢**：把成分股的月營收加總比去年同期，得出**整個產業的營收年增率**（39 個族群、184 檔）。
- **本益比**：近四季本益比每天自動抓官方公告；26/27/28 年預估本益比 = 現價 ÷ 預估 EPS，股價自動、預估自填。
  衡量的是產業景氣本身，不是股價漲跌
- 登記 **台股、期貨、選擇權、權證、複委託（USD）、現金、期貨權益數、負債**
- 自動算 **總資產、淨資產、槓桿①（資產槓桿）、槓桿②（曝險槓桿）**、目標達成率
- 一鍵存 **每日快照**，在「紀錄」看淨資產與槓桿的變化
- Email + 密碼登入，資料以 Row Level Security 隔離，只有自己看得到

## 1. 建立 Supabase 專案（免費）

1. 到 <https://supabase.com> 註冊，**New project**，區域選 Singapore 或 Tokyo（離台灣近）。
2. 左側 **SQL Editor → New query**，依序執行兩個檔案（都可重複執行）：
   - `supabase/schema.sql` — 建立資料表、RLS 政策與索引
   - `supabase/prices.sql` — 建立每日自動更新報價的排程
3. 左側 **Project Settings → API**，複製：
   - `Project URL`
   - `anon` `public` key
4. 打開 `config.js`，填入這兩個值：
   ```js
   export const SUPABASE_URL = 'https://xxxxxxxx.supabase.co';
   export const SUPABASE_ANON_KEY = 'eyJhbGciOi...';
   ```
   anon key 本來就是設計給前端用的，資料由資料庫的 RLS 保護，放在公開網頁沒問題。

## 2. 建立自己的帳號（建議做法）

個人使用最省事、也最安全的方式是**自己在後台建帳號、然後關閉公開註冊**：

1. **Authentication → Users → Add user → Create new user**，輸入 Email 與密碼，勾選 **Auto Confirm User**。
2. **Authentication → Sign In / Providers → Email**，關閉 **Allow new users to sign up**（可選，關掉後別人就不能在你的網站註冊）。

之後直接用網頁上的「登入」即可。若想改用網頁「註冊」功能也可以，Supabase 會寄確認信（免費方案每小時只有少量額度）。

## 3. 本機試跑

ES module 不能用 `file://` 直接開，需要一個靜態伺服器：

```powershell
cd asset-manager
python -m http.server 8000
# 開 http://localhost:8000
```

## 4. 部署到 GitHub Pages（讓手機可以用）

你已經有 `matthewhsieh.github.io` 這個 repo，把整個資料夾放進去即可：

```powershell
# 在 code 資料夾
Copy-Item -Recurse asset-manager matthewhsieh.github.io\asset-manager
cd matthewhsieh.github.io
git add asset-manager
git commit -m "add asset manager"

```

幾分鐘後網址是 **https://matthewhsieh.github.io/asset-manager/**

然後回 Supabase：**Authentication → URL Configuration**
- **Site URL** 填 `https://matthewhsieh.github.io/asset-manager/`
- **Redirect URLs** 加同一個網址（忘記密碼、註冊確認信會導回這裡）

1. Android Chrome 開上面的網址並登入。
2. 右上角選單 → **加到主畫面**，之後就像 App 一樣全螢幕開啟。
3. 登入狀態會保留，不用每次輸入密碼。

## 數字定義

| 名稱 | 公式 |
|---|---|
| 總資產 | 台股市值 ＋ 複委託市值×匯率 ＋ **期貨帳戶權益數** ＋ 現金/存款 |
| 淨資產 | 總資產 － 負債 |
| 槓桿①（資產槓桿） | 總資產 ÷ 淨資產 |
| 槓桿②（曝險槓桿） | （台股市值 ＋ 複委託市值 ＋ 期貨名目）÷ **總資產**，指數期貨與個股期貨都算 |
| 指數期貨名目 | 口數 × 結算價 × 每點價值（大台 200 / 小台 50 / 微台 10 / 電子 4000 / 金融 1000） |
| 個股期貨名目 | 口數 × 標的股價 × 等同股數（**大型 2,000 股 ＝ 2 張**、**小型 100 股**） |
| 期貨損益 | 多單（現價 − 平均成本）、空單（平均成本 − 現價），再乘口數與規格 |
| 已實現損益 | 賣出時（成交價 − 平均成本）× 賣出數量；期貨平倉時只結算平掉的口數。買進不計 |
| 當沖 | 記交易時勾「當沖」。買賣自成一組結算，**完全不動長期部位的股數與均價** |
| 已實現損益 | 顯示的一律是**扣掉手續費與交易稅之後的淨額**，買進那一筆的手續費也算在內 |

### 當沖為什麼要獨立處理

如果當沖的標的剛好是你長期持有的，用一般方式記會出兩個問題：
買進那一筆會把長期部位的均價拉歪（而且是永久的），
賣出時的已實現損益會變成「賣價 − 混合後均價」而不是「賣價 − 當沖買價」。

實測：持有 5 張均價 2000，當沖 1 張 2440 買、2500 賣。
不勾當沖會算成賺 426,667 且均價變成 2073；勾了當沖是正確的 60,000，均價維持 2000。

所以當沖的兩筆都要勾「當沖」。系統用**先進先出**把同一天同標的的當沖買賣配對，
**一趟來回算一組**，損益掛在平倉的那一筆上。先買後賣、先賣後買、部分沖銷都支援。

同一檔一天來回兩趟不會被平均在一起。例如買 518 賣 525、再買 511 賣 510，
會分別顯示 +14,000 和 −2,000，而不是合併成 +12,000 一個數字，
否則看不出哪一趟做錯。

**當沖只認你勾選的，不做推斷。** 早期用「同一天同標的有買有賣」推斷會出錯：
例如當沖 1 口的同時又賣掉 5 口長期部位，那 5 口會被誤判成當沖。

**代號可以打中文。** 打「台玻」會自動換成 1802。這很重要，
因為一組當沖若一筆填代號、一筆填中文，會被當成兩個標的而配不成對，損益就消失了。
既有紀錄即使當初填了中文，現在也會正確配對。

**只有台股現股當沖有證交稅減半，期貨、選擇權、權證都沒有。**
| 選擇權權利金市值 | 口數 × 權利金 × 50，買方為正、賣方為負，計入總資產 |
| 選擇權 delta 曝險 | 口數 × delta × 隱含遠期指數 × 50，取絕對值加總後計入槓桿② |
| 選擇權最大風險 | 買方 = 權利金；賣方賣權 =（履約價 − 權利金）× 口數 × 50；賣方買權無上限 |
| 權證市值 | 張數 × 1000 × 權證價，計入總資產 |
| 權證 delta 曝險 | 張數 × 1000 × 行使比例 × delta × 標的股價，計入槓桿② |
| 權證最大損失 | 付出的權利金。權證只能做買方，不會賠更多 |

> **算不出 delta 的部位不會被安靜地漏掉。** 權證或選擇權若還沒算出 delta，
> 總覽的曝險區塊會直接標示「這些部位目前沒有計入總曝險，實際曝險比顯示的高」。

### 權證：隱含波動率才是真正的風險

權證的委買賣價由發行券商決定，計價參數裡**唯一能在發行後被人為調整的就是隱含波動率**。
券商調降隱波會直接讓權證價格下跌，而 delta 完全反映不出這件事。

所以系統每天把每檔持有權證的隱波反推出來存進 `warrant_iv_history`，
比對期間內的變化，被調降超過 0.5 個百分點就在「持倉」標示「隱波被調降」。
這是這個工具比券商 App 多做的一件事。

約半數權證當天沒有成交，這時用造市商的委買賣中價評價。
界限型與重設型（約佔 7%）Black-Scholes 不適用，這類會標示並開放手動填 delta。

### 交易成本

稅率是法定的，寫死在程式裡（查證日期 2026-09-08）：

| 商品 | 交易稅 |
|---|---|
| 台股賣出 | 0.3% |
| **台股當沖賣出** | **0.15%**（已延長至 2027-12-31） |
| 權證賣出 | 0.1% |
| 期貨（含個股期貨） | 契約金額 × 0.002%，**買賣各課一次** |
| 選擇權 | 權利金 × 0.1%，**買賣各課一次** |

手續費因券商與折數而異，在「設定 → 交易成本」自己填：台股費率與折數、每筆最低、
權證折數、期貨每口、選擇權每口、複委託費率。

**折數是跟券商談的，當沖和波段都一樣。當沖影響的只有政府的證交稅（0.3% 減半為 0.15%）。**

**期貨與選擇權是每口固定金額，買進收一次、賣出再收一次**，所以一口來回等於填的兩倍。
複委託也是買賣各收一次。

成本是依交易紀錄即時算出來的，不存在每一筆裡，所以改了費率設定會全部重算，
也不會動到既有的交易紀錄。「買賣收益」的圖表畫的是**淨損益**，
買進那一筆的手續費也算在內。

### 選擇權的 delta 怎麼算出來的

不折現的 Black-76 模型裡，理論價只取決於遠期價 F、履約價 K 與 `σ√T` 這個合成參數，
所以由市場權利金可以直接解出 `σ√T`，**不需要分別知道到期日與波動率**，
也就避開了期交所到期代碼（`202609` / `202609W2` / `202609F2`）換算成日期的麻煩。

遠期價 F 用選擇權鏈自己的買賣權平價反推（`F = K + C − P`，取價平那組），
與權利金同一天同一市場，不受期貨行情發布延遲影響。
實測買賣權平價檢查 `call delta − put delta = 1.000`，資料庫與參考實作的結果分毫不差。

**但書：** delta 曝險是線性近似。大幅波動時實際曝險會被 gamma 放大，賣方尤其明顯。
所以最大風險是獨立顯示的數字，不併進槓桿。

> 期貨的「權益數」是帳戶層級的一個數字，記在「資金」頁，只計入總資產一次；
> 各個部位的「名目金額」只影響曝險，不會重複計入資產。

## 每日自動更新

全部在 Supabase 資料庫裡用排程跑，手機關著也會更新，也不會用到你的電腦。

| 時間（台灣） | 內容 |
|---|---|
| 交易日 14:30 / 16:00 / 18:00 / 21:00 | 台股收盤價、期貨結算價、美金匯率、**本益比與月營收**、當日快照 |
| 交易日隔天 06:00 | 美股收盤價 |

一天跑四次是因為**來源可能比排程晚發布**。抓到當天資料後，後面幾次會被守則擋掉，
不會重複下載（實測完整流程從 6 秒降到 1.5 秒，且不再打對方的 API）。
上市與上櫃各自判斷，其中一邊晚發布不會影響另一邊。

| 資料 | 來源 | 備註 |
|---|---|---|
| 上市股票 | 證交所「每日收盤行情」`MI_INDEX`，帶日期 | 以台北時區的日期往回找最近一個交易日。**不要用 `STOCK_DAY_ALL`**，實測會落後好幾天 |
| 上櫃股票 | 櫃買中心 `tpex_mainboard_daily_close_quotes` | 永遠回最新交易日 |
| 選擇權結算價 | 期交所 `DailyMarketReportOpt` | 實測比期貨那份新，含履約價、買賣權、結算價 |
| 權證基本資料 | 證交所 `t187ap37_L` | 20MB、37,000 筆，只有除權息才會變，**每 6 天才重抓一次** |
| 權證每日報價 | 證交所 `MI_INDEX` type=0999 / 0999P | 含標的代號與標的收盤價，約 31,000 筆 |
| 指數期貨結算價 | 期交所 `DailyMarketReportFut` | 這個端點會在 JSON 與 CSV 間變換格式，程式兩種都吃；期交所發布本身有延遲 |
| 美金匯率 | Yahoo `TWD=X` | 期交所那份會落後數日，只當備援 |
| 美股 | Yahoo Finance | 只抓實際持有的代號。估值端點已改成要 crumb 驗證，抓不到本益比 |
| 本益比・淨值比・殖利率 | 證交所 `BWIBBU_ALL`、櫃買中心 `tpex_mainboard_peratio_analysis` | 全市場 1,969 檔，官方每日公告，是近四季不是預估 |
| 月營收 | 證交所 `t187ap05_L`、櫃買中心 `mopsfin_t187ap05_O` | 每月 10 日前後更新。**單位是仟元**，1 億 = 100,000 |

每個市場的資料日期會顯示在「設定 → 行情更新」，若某個來源落後，總覽會直接標示，不會讓你誤以為是最新價。
每筆快照也會記錄 `price_as_of`（這筆是用哪一天的收盤價算的），在「紀錄」頁的「行情日」欄位；
若它比快照日期早會標紅，表示當時來源還沒發布。自動快照隔幾小時會用新價格覆蓋自己，會自動收斂到正確值。

- 個股期貨用**標的股票收盤價**計價，因為曝險的定義就是「等同 N 股現股」。
- 價格只會 `UPDATE`，**不會新增或刪除任何項目**；只有賣光時部位才會被移除。
- 想立刻更新：App 右上角 ↻，或到「設定 → 立即重新抓取報價」，約 6 秒。

> **為什麼手動更新是一項一項抓的。** Supabase 給 `authenticated` 角色的 statement_timeout 是 **8 秒**，
> 但七個來源一次跑完要 10 秒以上，權證基本資料更要 50 秒，所以一定會逾時。
> 手動更新改成呼叫 `refresh_market(kind)` 一次做一項，每項都遠低於 8 秒，
> 某一項失敗也不影響其他項。權證基本資料 20MB 不放進互動流程，只由排程處理。
> 目前的階段是 `tw` `fut` `opt` `war` `fx` `us` `val` `rev` `sync`。
- 排程狀態可查：SQL Editor 執行 `select * from price_runs order by id desc limit 20;`
- 各市場資料日期：`select * from price_status;`

想改定義，只要改 `app.js` 裡的 `compute()`。

## 記一筆交易的規則

| 情境 | 處理 |
|---|---|
| 台股 / 美股 買進 | 股數相加；均價 =（原股數×原均價 ＋ 新股數×成交價）÷ 總股數；現價更新為成交價 |
| 台股 / 美股 賣出 | 股數相減；均價不變；賣到 0 自動移除部位；賣超過持有會擋下 |
| 期貨 | 以淨口數計算：買進 +、賣出 −；穿越 0 自動翻多／翻空；歸零移除部位。新部位的「帳戶權益」要到持倉頁補填 |
| 刪除交易 | 若是該標的最新一筆，精確還原到交易前；否則只反向調整數量（均價不動） |
| 台股單位 | 預設「張」（1 張 = 1000 股），可切換成「股」 |

交易本身不會動現金餘額，現金請在「資金」頁自行維護。

## 族群趨勢怎麼算的

台灣強制上市櫃公司每月公告營收，是全球少見的高頻基本面資料。多數市場只有季報。

把一個族群的成分股營收加總，再比去年同月，就是這個產業的實際成長率。
比看股價漲跌更接近「產業趨勢」本身，因為股價已經含了預期與情緒。

族群分類在 `supabase/themes.sql`，人工維護，改完整段重跑即可。
目前 **39 個族群、184 檔**，從上游玻纖布一路到機殼、快接頭、探針卡、無塵室廠務。

分類原則是**寧可拆細也不要合併**。被動元件裡 MLCC、石英元件、電阻電感是三個完全不同的循環，
合在一起看只會互相抵銷掉訊號。一檔可以屬於多個族群（台玻同時在玻纖布與玻璃基板），各族群獨立加總。
族群至少三檔，只有一兩檔的「族群」其實是個股：銅箔（金居）與玻璃基板（台玻、富喬）是僅有的例外，
因為台灣純做這兩塊的上市公司就是這麼少，看它們的數字時要記得那其實是個股營收。

每筆營收公告都含「當月、上月、去年當月」三個數字，所以抓一次就能寫進三個月份，
歷史會隨每月公告自然累積，不需要另外補歷史資料。

**營收成長不等於股價會漲。** 但產業景氣的轉折通常先反映在營收，而營收是硬數字。

## 本益比怎麼來的

這頁分成兩件性質完全不同的事，混在一起看會出事。

### 近四季本益比：是事實，全自動

證交所與櫃買中心**每天公告**每一檔的本益比、股價淨值比與現金殖利率，
上市走 `BWIBBU_ALL`、上櫃走 `tpex_mainboard_peratio_analysis`，
存進 `valuation` 表，跟股價一起每天自動更新，不需要任何人工輸入。
涵蓋 1,969 檔，其中約 1,540 檔有本益比。

虧損的公司顯示「虧損」而不是 0。顯示 0 會讓人誤以為很便宜，那是最危險的誤讀。

### 26 / 27 / 28 年預估本益比：是猜測，要自己維護

公式是 **現價 ÷ 預估 EPS**。股價每天自動更新，所以比值每天都會變，這部分是自動的。
但**分母沒有免費 API**。台灣的分析師共識預估在 FactSet、彭博與券商報告裡，都要付費。

所以做法是把預估 EPS 存在資料庫：

| 表 | 用途 |
|---|---|
| `eps_forecast` | 共用參考值，人工整理自公開報導與券商報告，含來源、分析師人數與可信度 |
| `eps_override` | 你自己的預估，受 RLS 保護，填了就以你的為準 |

在「持倉」頁點任一列就能填。留空就退回共用參考值。資料檔是 `supabase/eps_forecast.sql`。

**預估本益比的分母是別人的猜測。** 同一檔股票不同券商的 2028 年 EPS 可以差一倍，
算出來的本益比自然也差一倍。所以每筆預估都存來源與查證日期，三個月就該重看一次。

#### 覆蓋度：這才是最容易誤判的地方

同樣顯示成「26F 幾倍」，背後可能是 42 位分析師的共識，也可能是某篇新聞引述的無名「法人」。
所以每一筆都存分析師人數與可信度，**而且是逐年存的**，因為同一檔的不同年度差很多：

| 標的 | 2026 | 2027 | 2028 |
|---|---|---|---|
| 台積電 2330 | 42 位 | 42 位 | 42 位 |
| 奇鋐 3017 | 19 位 | 19 位 | 19 位 |
| 和碩 4938 | 9 位 | 9 位 | **1 位** |
| 神達 3706 | 4 位 | 無 | 無 |
| 金居 8358 | 2 位 | **1 位（只有高盛）** | **1 位（只有高盛）** |
| 台玻 1802 | **0 位（新聞引述無名法人）** | 無 | 無 |

人數少於兩位或沒有具名機構的，那一格會標 ⚠，整檔沒有任何像樣覆蓋的會標「無分析師覆蓋」。
一位分析師的預估不叫一致預期。

#### 達成率

年初至今已實現 EPS ÷ 當年度預估。季報 EPS 來自證交所 `t187ap14_L` 與櫃買 `mopsfin_t187ap14_O`，
存在 `financials` 表，欄位是**年初到該季的累計值**，所以第 2 季就是上半年。

半年報時達成率應該在 50% 上下。明顯偏低就代表那個預估在賭下半年大爆發，
**這件事光看預估本益比是完全看不出來的**。目前四檔持股的達成率都在 38–42%，全部押在下半年。

### 複委託的美股

Yahoo 的估值端點現在要 crumb 驗證，抓不到近四季本益比，所以那一欄是空的。
但股價一樣每天自動更新，只要自己填了預估 EPS，預估本益比照樣會每天重算。

### 族群本益比

「族群」頁每個族群顯示成分股本益比的**中位數**，不是平均。
一檔異常高就會把平均拉爛，中位數不會。虧損的公司不計入中位數，
但會另外標出有幾檔在虧損，那本身就是訊息。點開族群可以看到每一檔的本益比。

## 資料安全

**更新程式不會動到已輸入的資料與買賣紀錄。** schema 變更一律只做 `add column if not exists`
這類新增動作，不 drop、不 rename、不重算既有的部位、成本與交易。
排程只會更新 `price` 欄位；股數、口數、成本、金額這些你輸入的數字永遠不動。
